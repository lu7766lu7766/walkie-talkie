# 📻 對講機 Walkie-Talkie

用瀏覽器開啟就能使用的即時對講機，可安裝成 App（PWA）。建立房間、分享連結，聲音即時傳給房間裡的每個人。

- **房間**：在大廳一鍵建立新房間，把邀請連結分享給別人，對方點連結、或在大廳貼上連結就進到同一個房間；大廳不列出任何房間，**只有拿到邀請連結的人進得來**；按左上角 ‹ 回到大廳
- **暱稱**：在大廳或邀請頁修改，自動儲存，之後開啟都沿用
- **AI 降噪與人聲辨識**：RNNoise 消除風聲、引擎等環境噪音；音量門檻與 AI 人聲判斷交叉比對，確定是人在說話才傳送，門檻可自行調整

- **按住發話（預設）／自動偵測（即時監聽）**：預設按住發話鍵才傳送；發話鍵下方切到「自動偵測」後，偵測到你說話就自動傳送，別人即時聽到
- **按住說話**：螢幕大按鈕、鍵盤（預設空白鍵），或「模擬鍵盤」的藍牙 PTT 按鈕
- **耳機／藍牙耳機按鍵**：按一下播放鍵開始、再按一下結束（限制說明見下方）
- **房主管理**：建立房間的人是房主，可以關閉別人的自動偵測，或禁言一直佔線的人
- **麥克風只在需要時詢問**：自動重試只在已允許時進行，不會一直跳出詢問視窗
- **同一時間只有一人能說話**（半雙工），跟真的對講機一樣；別人在講時按下會聽到忙線音。每個房間最多 50 人同時收聽
- 開始／結束提示音（roger beep）、說話者顯示、成員列表、斷線自動重連
- **通話文字**：每段發話結束後自動轉成文字並校正（Workers AI），顯示在房間最下方：時間、發話人、內容，右邊 ▶ 可重播語音，新的在上，1 分鐘後淡出
- **背景執行與播放**：切到其他 App 或鎖屏後繼續收聽；鎖定畫面／通知列顯示誰正在說話
- PWA：可加入主畫面、全螢幕執行、離線也能開啟 App 外殼

## 畫面

簡約清新風格，淺色為主、跟著系統自動切換深色模式。房間頁只留最常用的東西：

- **頂列**：‹ 退出、房間名稱與在線人數、邀請、設定
- **中間**：狀態（房間空閒／誰正在說話／發話秒數）、大發話鍵、「按住發話／自動偵測」切換
- **下方**：通話紀錄
- 點房間名稱打開「成員」面板（房主可在這裡管理成員）
- 邀請（QR code、複製連結與代碼、成員）與所有設定（發話鍵方式、PTT 按鍵、耳機、降噪、音量、背景播放、螢幕常亮）都收在從下方滑出的面板，點面板外面或 ✕ 關閉

## 架構與技術選型

```
┌──────────── 瀏覽器／PWA ────────────┐            ┌──────── Cloudflare ────────┐
│ 麥克風 → AudioWorklet（RNNoise 降噪）│            │ Worker（靜態網頁 + API）    │
│   → 降頻 16 kHz → μ-law 編碼        │  WebSocket │   /api/channel/:id/ws       │
│   → 每 40 ms 一個語音框 ────────────┼──────────► │      │                      │
│                                     │            │      ▼                      │
│ 收到的語音框 → 抖動緩衝 → 喇叭      │ ◄──────────┼─ Durable Object（一房間一個）│
│                                     │            │   ・成員名單                │
│ 發話鍵：螢幕／鍵盤／耳機            │            │   ・發話權（一次一人）      │
└─────────────────────────────────────┘            │   ・語音框轉發給其他成員    │
                                                   └─────────────────────────────┘
```

| 部分 | 技術 | 原因 |
| --- | --- | --- |
| 前端 | Vite + TypeScript（無框架） | 介面只有兩頁，不用框架，bundle 只有約 6 KB gzip |
| 音訊擷取 | AudioWorklet | 在音訊執行緒上即時處理，延遲最低，所有主流瀏覽器都支援 |
| 語音編碼 | G.711 μ-law，16 kHz 單聲道（128 kbps） | 零相依、幾行程式就能實作、所有瀏覽器都能解碼；音質就是清楚的對講機音質 |
| 傳輸 | WebSocket | 穿透各種 NAT／防火牆／公司網路都沒問題，不需要 TURN 伺服器 |
| 後端 | Cloudflare Workers + Durable Objects | 見下一節 |
| 部署 | Cloudflare Workers（前後端一起） | 一次部署、同網域、不用設定 CORS |

### 為什麼需要後端？純前端不行嗎？

不行。瀏覽器之間要互相找到對方，至少需要一個「信令伺服器」交換連線資訊，純靜態網站（例如只放 Vercel）做不到。
即使改用 WebRTC 點對點，一個人說話時也要把聲音同時上傳給房間裡**每一個人**（mesh），人一多，手機上傳頻寬和電量就撐不住。

對講機的特性是「同一時間只有一個人說話、其他人都在聽」，最適合的做法是「伺服器轉發」：說話者只上傳一份，伺服器複製給所有人。

### 為什麼選 Cloudflare 而不是 Vercel？

Vercel 的 Serverless Functions 不支援長時間的 WebSocket 連線，而 Cloudflare **Durable Objects** 正好適合這種情境：

- 每個房間對應一個 Durable Object，天生就是「這個房間的唯一協調者」，處理發話權不會有競爭問題
- 使用 **WebSocket Hibernation**：沒人說話時 DO 會休眠，不計執行時間；心跳 ping/pong 由平台自動回覆，不會喚醒它
- 全球邊緣節點，DO 會建在第一個進入房間的人附近
- SQLite 型 Durable Object 在 **Workers 免費方案**就能使用

**結論：Cloudflare 完全夠用，前後端都放在同一個 Worker。**
如果還是想把前端放 Vercel，也可以：建置時設定 `VITE_API_ORIGIN=https://你的-worker.workers.dev`，前端就會連到 Cloudflare 上的後端。

### 免費額度大概能用多少？

（數字以 Cloudflare 官方定價頁為準，以下為估算）

- 每個說話中的人每秒送出 25 個語音框；DO 的 WebSocket 收到的訊息以 20:1 計為請求數
- 免費方案每天 100,000 次 DO 請求 ≈ 200 萬個語音框 ≈ **每天約 22 小時的累計發話時間**
- 聽的人不影響請求數（伺服器送出的訊息不計費）；頻寬方面每個收聽者約 128 kbps

小團隊日常使用免費方案綽綽有餘；量大時升級 Workers Paid（每月 5 美元起）。

## 房間

| 網址 | 畫面 |
| --- | --- |
| `/` | 大廳：編輯暱稱、建立新房間、貼上邀請連結（或房間代碼）加入。**不列出任何房間** |
| `/r/<代碼>` | 邀請頁：點邀請連結進來的人看到房間代號與目前人數，按「進入房間」就加入 |

- **防止亂入**：房間代碼是 128 bit 隨機值（網址裡 22 個字元，例如 `/r/lWnfsojK-Z7zrZY5lYVong`），不可能被猜到或列舉；伺服器也沒有任何列出房間的 API。要進入房間只能靠邀請連結
- **從主畫面 PWA 開啟的人**：iPhone 點邀請連結一定會開到 Safari（不會進主畫面的 App），所以大廳有「貼上邀請連結」：在聊天 App 長按連結複製，回到 App 按「📋 貼上」就直接進房間（整段 LINE 訊息貼上也看得懂）。Android 已安裝的 PWA 在支援的情況下會直接用 App 開啟邀請連結（manifest 的 `handle_links` / `launch_handler`）
- 房間頁右上角的「邀請」圖示（或點房間名稱）打開邀請面板：**邀請 QR code**（點一下全螢幕放大，旁邊的人用手機相機掃描就能加入）、**分別複製邀請連結或房間代碼**、「分享邀請連結」用 LINE 等 App 傳送，下方是房間成員。「lWnf」是代碼前 4 碼，只用來口頭確認大家在同一個房間，光靠它進不了房間
- 暱稱在大廳或邀請頁修改時就自動存到瀏覽器（localStorage），之後開啟、換房間都沿用
- 按左上角 ‹ 或瀏覽器的「上一頁」回到大廳
- 瀏覽器規定一定要使用者點一下才能開麥克風與播放聲音，所以點連結後需要再按一次「進入房間」，無法完全自動進入
- 沒有人的房間不佔任何資源（Durable Object 會自動休眠），不需要刪除房間

## 房主管理（避免有人一直佔線）

建立房間的人就是**房主**（房間標題下方顯示「你是房主」）。點房間名稱打開「成員」面板：

- 每個人旁邊會顯示「說話中／自動偵測／已禁言」
- **關閉自動偵測**：對方開著自動偵測忘了關、把旁邊的聊天都傳出來時，按一下就幫他改回按住發話（對方會收到通知，之後可以自己再打開）
- **禁言**：被禁言的人只能收聽、不能發話；正在說話會立刻被切斷。重新整理頁面也還是禁言，直到房主按「解除禁言」
- **全部關閉自動偵測／全部禁言／全部解除禁言**：一次處理房主以外的所有人
- 有人正在說話時，房主的狀態列下方會直接出現「禁言 某某」按鈕，不用打開面板

說明與限制：
- 房主只能**關閉**別人的自動偵測，不能遠端打開別人的麥克風傳送
- 房主身分綁定「建立房間的那台裝置的那個瀏覽器」：每台裝置有一把隨機密鑰（存在 localStorage），用它對房間代碼算出房主金鑰，伺服器只存金鑰的雜湊。所以房主離開再回來仍是房主，別人拿到邀請連結也冒充不了；裝置上也不會記下任何房間代碼。清除瀏覽器資料、換裝置或換瀏覽器就失去房主身分（目前不能轉移房主）
- 只有「房間裡還沒有別人、也還沒有房主」時才能宣告成為房主，所以功能上線前建立的舊房間沒有房主
- 禁言記在發話者這個分頁上（重新整理仍有效）；如果對方另開新分頁重新進入，就要再禁言一次

## 麥克風權限：為什麼會一直被問、怎麼避免

「要不要允許麥克風」是瀏覽器決定的，網頁沒辦法替使用者按允許，只能**不要多問**並**教使用者設成一律允許**：

- 整個網頁只開一次麥克風，換房間、回大廳都沿用，不會重新詢問
- 自動重新取得麥克風（點畫面、回到前景、被系統收走後重試）**只在瀏覽器已經允許時**才進行；還沒允許或按了拒絕，就不會自己一直跳出詢問視窗，要按「重新偵測麥克風」或發話鍵才會再問一次
- 同一台裝置被詢問第 2 次起，房間裡會出現「每次都要按允許麥克風？」的設定說明（依平台顯示，按「知道了」就不再出現）：
  - Android Chrome／電腦：詢問時選「每次造訪時都允許」，不要選「僅限這次」
  - iPhone Safari：網址列左邊「大小」→「網站設定」→「麥克風」→「允許」，或「設定」App →「Safari」→「麥克風」→「允許」
  - Firefox：勾選「記住這項決定」
  - iPhone 主畫面 App：iOS 可能在每次重新開啟 App 時詢問，這是系統的限制

## 噪音抑制與人聲辨識

麥克風的聲音在音訊執行緒上依序處理：

```
麥克風 → 瀏覽器內建降噪 → 重新取樣 48 kHz → RNNoise AI 降噪（同時算出人聲機率）
      → 人聲閘門（不是人聲就靜音）→ 16 kHz μ-law → 送出
```

1. **AI 降噪**（[RNNoise](https://jmvalin.ca/demo/rnnoise/)，約 114 KB）：消除風聲、引擎、冷氣、人群等持續噪音。
2. **只傳送人聲**：AI 判斷不是人聲的片段直接靜音，**按住發話時也適用**。閘門會往後多看 20 ms 再決定開關，開口第一個字不會被切掉；說完後保持 300 ms，句中換氣不會被靜音。
3. **交叉辨識**（即時監聽）：以下兩個條件**同時成立**才算有人在說話，才會開始傳送：
   - 音量高於「噪音門檻」，而且比自動追蹤的環境噪音底線高出 10 dB
   - AI 判斷的人聲機率高於「人聲辨識嚴格度」

可在房間右上角「設定」的「降噪」區調整（打開設定時會顯示即時音量條，方便對照門檻）：

| 設定 | 預設 | 用途 |
| --- | --- | --- |
| AI 降噪 | 開 | 關閉後只用瀏覽器內建降噪 |
| 只傳送人聲 | 開 | 非人聲時靜音 |
| 噪音門檻 | -45 dB | 低於這個音量一律當成環境音。**風大、很吵的地方往右調高** |
| 人聲辨識嚴格度 | 60% | 越高越不容易被環境音觸發，但小聲說話可能被忽略 |

面板打開時會顯示即時音量條（白線是噪音門檻）與「人聲 %」，可以邊講邊調。

實測（用模擬強風 -15 dBFS 的錄音當麥克風輸入）：

| 情境 | 結果 |
| --- | --- |
| 即時監聽 + AI 降噪，強風中沒人說話 8 秒 | 0 次誤觸發 |
| 即時監聽，關閉 AI，同樣情境 | 一直在傳送風聲 |
| 按住發話 2 秒，關閉所有降噪 | 對方收到 -26 dBFS 的風聲 |
| 按住發話 2 秒，AI 降噪 | 對方收到 -75 dBFS（降低約 50 dB） |
| 按住發話 2 秒，AI 降噪 + 只傳送人聲 | 對方收到完全靜音 |

限制：風聲遠大於人聲時（例如麥克風直接被風吹），AI 也可能把整段當成噪音而不傳送。這時建議戴有防風棉的耳機麥克風，或把「人聲辨識嚴格度」調低。

## 自動偵測／即時監聽（聲控發話）

進入房間後麥克風就一直開著，但**只有偵測到說話時才傳送**，安靜時不送任何資料。發話鍵下方的「按住發話／自動偵測」可以隨時切換，切回「按住發話」就是一般的對講機。

運作方式：

1. AudioWorklet 持續把麥克風轉成 40 ms 的語音框，同時算出濾掉 150 Hz 以下低頻後的音量
2. `src/client/vad.ts` 交叉比對音量與 AI 人聲機率（見上一節），判斷是否在說話：
   - 自動追蹤環境噪音底線，換到吵雜環境不會一直誤觸發
   - 連續 80 ms 超過門檻才開始，濾掉敲桌子、咳嗽這類短促聲音
   - 安靜 800 ms 才結束，句子中間換氣不會被切斷
3. 判定開始說話 → 向伺服器要發話權，並把**偵測到之前的 320 ms 一起補送**，第一個字不會被吃掉
4. 判定說完 → 送完最後一個框後釋放發話權

避免誤觸發的保護：

- **別人在說話、或喇叭還在出聲時暫停偵測**：喇叭的聲音被自己的麥克風收進去，不會被當成自己在說話
- 兩人同時開口時，沒搶到發話權的一方安靜退讓（不播忙線音），1.5 秒後再開始偵測
- 聲控發話不播開始／結束提示音（會被麥克風收進去，而且一句一聲太吵）

開關旁的音量條會即時顯示你的音量與噪音門檻（白線），「人聲 %」顯示 AI 的判斷。

### 麥克風一直保持開啟

- 關閉即時監聽**不會**關掉麥克風，只是停止自動偵測，麥克風仍在運作，按住說話立刻就能用
- 換房間、退出回大廳也不會關麥克風，整個網頁只開一次。原因是部分手機瀏覽器關掉麥克風後再開會失敗、或拿到沒有聲音的串流；iOS 也限制同一頁能建立的音訊環境數量
- 麥克風被系統收走時（來電、其他 App 搶用、iOS 切到背景）會自動重新取得：串流結束 1 秒後重試，之後每次點畫面或回到前景也會再試
- 大廳會顯示「麥克風維持開啟中」，想釋放可以按「關閉麥克風」；關閉網頁也會釋放

### 沒有麥克風也能進房間收聽

電腦沒接麥克風、系統停用麥克風、權限被拒，或在 LINE 等 App 的內建瀏覽器裡打開時，仍然可以進入房間**收聽**：

- 房間頁會顯示原因與解法（例如「找不到麥克風，請接上耳機麥克風；Windows：設定 → 隱私權與安全性 → 麥克風」）
- 發話鍵顯示「沒有麥克風・只能收聽」；接上麥克風或改好權限後按「重新偵測麥克風」，偵測到就能直接說話
- 邀請連結帶有 LINE 的 `openExternalBrowser=1` 參數，在 LINE 裡點開會直接用手機預設瀏覽器開啟；在其他 App 內建瀏覽器開啟時，邀請頁會提示改用 Chrome 或 Safari
**建議戴耳機使用**，用喇叭外放時，雖然有回音保護，對方聲音的尾巴仍可能偶爾誤觸發。

即時監聽開著的時候，螢幕按鈕、鍵盤、耳機按鍵仍然可以手動發話。

## 通話文字（語音轉文字＋自動校正）

房間下方的「通話紀錄」會顯示每段發話的**時間、發話人與內容**，右邊的 **▶ 可以重播那段語音**，新的在上面，出現 1 分鐘後自動淡出。

```
發話結束 → Durable Object 把剛轉發過的這段語音轉成 WAV
        → Workers AI Whisper（@cf/openai/whisper-large-v3-turbo）辨識成文字
        → Workers AI Qwen3（@cf/qwen/qwen3-30b-a3b-fp8）校正同音錯字、補全形標點、轉繁體
        → 廣播給房間所有人
```

- 畫面依序顯示「辨識中…」→ 辨識結果（標示「校正中…」）→ 校正後的文字（閃一下表示已校正）
- 伺服器本來就在轉發語音，所以**不分瀏覽器、沒有麥克風只能收聽的人也看得到**
- 不辨識：短於 0.6 秒的發話、幾乎沒有聲音的發話（例如被人聲閘門靜音）；也會濾掉 Whisper 在雜音上常見的「幻覺」輸出（「字幕由 Amara.org 社群提供」「請不吝點贊訂閱」等）
- 校正結果跟原文長度差太多（模型自己發揮）就保留原文；AI 失敗或逾時（例如當天免費額度用完）會顯示「無法辨識，可按右邊重聽」，不影響通話
- **▶ 重播**：辨識再準也難免聽錯人名、數字、地名，所以每筆都能重聽原音。語音是每支手機收到時順便留在記憶體的一份，不經伺服器、不多花流量，通話文字淡出就刪掉；剛進房間前的紀錄沒有語音可重播
- 剛進房間的人會看到最近一分鐘的紀錄；紀錄只存在記憶體，不會永久保存

**費用與隱私：** 會用到 Workers AI 的額度（免費方案每天有固定免費額度，Whisper 以音訊分鐘計價、很便宜，實際用量可在 Cloudflare 後台 Workers AI 頁面查看）。語音會送到 Cloudflare Workers AI 處理；不想使用可以把 `wrangler.jsonc` 裡的 `"ai"` 設定拿掉，就不會產生通話文字。

**本機開發：** Workers AI 只能連到 Cloudflare 執行，本機預設不連（不用登入），所以不會產生通話文字。要測試畫面流程可以在專案根目錄建立 `.dev.vars`，寫入 `TRANSCRIBE_FAKE=1`，會產生假的辨識結果（`TRANSCRIBE_FAKE=fail` 模擬 AI 出錯；改完要重新 `npm run build` 或重啟 `npm run dev`）；已 `npx wrangler login` 想用真的 AI，執行時加上 `CLOUDFLARE_REMOTE_BINDINGS=1`。

## 耳機／藍牙按鍵：能做到什麼、做不到什麼

| 裝置 | 運作方式 | 支援「按住」？ |
| --- | --- | --- |
| 螢幕按鈕 | Pointer Events | ✅ 按住說話、放開結束 |
| 鍵盤 | keydown／keyup（可在設定中重新綁定任意鍵） | ✅ |
| **藍牙 PTT 按鈕**（市售對講機用的那種，多半模擬成鍵盤） | 同鍵盤，在設定中按「重新綁定」再按一下 PTT 按鈕即可 | ✅ |
| 有線耳機線控、藍牙耳機的播放／暫停鍵 | Media Session API | ⚠️ 只有「按一下」，**按一下開始、再按一下結束** |

說明：

- 瀏覽器對耳機按鍵只會收到「播放／暫停」這種單次事件，**拿不到「按下」和「放開」**，所以耳機一律是切換模式。這是網頁平台的限制，原生 App 才能做到真正按住。
- 瀏覽器只會把媒體鍵交給「正在播放媒體」的網頁，所以 App 進入房間後會循環播放一段無聲音訊來佔住媒體控制。
- 麥克風啟用時，藍牙耳機會切換到通話模式（HFP）。部分手機在這個模式下會把耳機按鍵當成「接聽／掛斷」而不是「播放／暫停」，這時按鍵可能沒反應，依手機與耳機型號而異。**最穩定的方案是買一顆藍牙 PTT 按鈕（HID 鍵盤型）**。

## 背景執行與播放

行動瀏覽器會暫停「沒在播放媒體」的背景網頁，所以這裡的做法是**讓系統把對講機當成音樂 App**：

1. 收到的聲音不直接送到喇叭，而是經由 `MediaStreamAudioDestinationNode` 導進一個持續播放的 `<audio>` 元素。系統看到「正在播放媒體」，切到背景或鎖屏時就不會暫停網頁，WebSocket 與 AudioContext 都持續運作
2. 用 Media Session API 在鎖定畫面／通知列顯示「🔊 小明 正在說話」、房間代號與人數
3. 心跳改成「ping 送出後 10 秒沒回應才算斷線」，不再依賴計時器準時（背景分頁的計時器會被延後到最慢一分鐘一次，舊做法會在背景誤判斷線）
4. **音訊卡住自動恢復**：瀏覽器的音訊輸出偶爾會停止更新（AudioContext 被系統暫停或中斷、背景播放的 `<audio>` 元素停住），症狀是喇叭不斷重複最後一小段聲音。每 0.4 秒檢查一次：被暫停就喚醒；時間連續兩次沒前進就重新啟動 AudioContext，或重新接上 `<audio>` 的串流清掉舊緩衝；重播該結束卻沒收到結束事件就強制停止。原本要使用者再點一下才會恢復
4. 回到前景時自動：喚醒被系統暫停的 AudioContext、重新取得被 iOS 關掉的麥克風、恢復耳機按鍵、重新保持螢幕常亮

設定裡可以分別開關「背景播放」與「保持螢幕常亮」。若某支手機在背景播放模式下聲音異常，關掉「背景播放」即恢復成直接輸出到喇叭。

| 平台 | 背景／鎖屏收聽 | 背景／鎖屏發話 |
| --- | --- | --- |
| Android Chrome／已安裝的 PWA | ✅ | ✅ 用耳機播放鍵或藍牙 PTT 按鈕（麥克風在背景持續運作，通知列會顯示使用中） |
| iPhone Safari／已安裝的 PWA | ⚠️ 視 iOS 版本，系統可能在一段時間後暫停 | ❌ iOS 在背景一律關閉網頁的麥克風 |
| 桌面瀏覽器 | ✅（最小化視窗也可以） | ✅ 視窗在前景時可用鍵盤 |

iPhone 預設開啟「保持螢幕常亮」，需要長時間值勤時這是最穩定的用法。要在 iPhone 上做到鎖屏收聽與發話，只能包成原生 App（見後續規劃）。

### 發話流程

1. 按下發話鍵 → 立刻開始錄音（先存在本地），同時向伺服器要發話權
2. 伺服器同意 → 把剛剛先錄的部分一起補送，接著即時串流；**第一個字不會被吃掉**
3. 伺服器拒絕（別人正在講）→ 丟棄錄音，播放忙線音
4. 放開 → 等最後半個語音框送完，再釋放發話權，其他人聽到 roger beep
5. 單次發話上限 60 秒；若某人斷線卡住發話權超過 65 秒，下一個人按下時會強制收回

### 安全性

- 房間代碼是 128 bit 隨機值，只存在於邀請網址裡；Worker 只收到它的 SHA-256 雜湊，也沒有列出房間的 API
- 這是「拿到邀請連結就能進入」的模式，**沒有帳號驗證**：連結被轉傳出去，收到的人也進得來。需要更嚴格時可以加房主核准或踢人（見後續規劃）。語音在傳輸中有 TLS 加密，但會經過 Cloudflare 伺服器轉發（不是端對端加密），通話文字功能也會把語音送到 Cloudflare Workers AI 辨識

## 後續規劃（建議優先順序）

1. **Opus 編碼**：用 WebCodecs `AudioEncoder` 改成 Opus（約 24 kbps），頻寬省 80%，音質更好；不支援的瀏覽器自動退回 μ-law
2. **原生 App 外殼（Capacitor）**：iPhone 鎖屏收聽與發話（背景音訊模式）、真正的藍牙耳機「按住」
3. **Web Push 通知**：App 完全關閉時，有人在房間說話就推播通知（iOS 16.4 以上已安裝的 PWA 也支援），點一下回到房間
4. **帳號與房間管理**：登入（Cloudflare Access 或 OAuth）、房間密碼或成員白名單、房主踢人
5. **多房間監聽**：同時聽多個房間，類似對講機的掃描功能
6. **錄音回放**：把每段發話存到 R2，錯過的訊息可以回放
7. **改用 WebRTC SFU**（Cloudflare Realtime）：如果需要更低延遲（< 150 ms）或上百人的大房間
